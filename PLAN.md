# План: VLESS + REALITY с nginx-заглушкой и опциональным выходом через Cloudflare WARP

Версия 1.0 · 2026-10-31 · план зафиксирован

## 0. Зафиксировано

- сервер: Ubuntu 22.04, публичные IPv4 и IPv6; IPv4 блокируется только у вашего провайдера, IPv6 работает;
- домены есть (два + поддомены); SNI и сертификат — ваш домен, указывающий на IPv6 VPS;
- клиент подключается по IPv6-литералу: в ссылке `[IPv6]:443` + `sni=домен` (AAAA может ещё не резолвиться — на подключение это не влияет);
- один пользователь + команда `--add-user`, которая печатает готовую ссылку;
- выход Xray — весь трафик через WARP, с откатом на direct, если WARP недоступен;
- опция блокировки RU-направлений (`.ru`, `.рф`, `.su`, `geoip:ru`) — чтобы сервер не светился запросами в российский сегмент;
- 443 — Xray (self-steal), nginx — 80 и 127.0.0.1:8443;
- основная фильтрация, что отправлять в туннель, — на стороне клиента.

## 1. Задача

Установочный скрипт (bash, без GUI) для VPS:

- вход по TCP 80 и 443, IPv4 + IPv6;
- VPN на Xray: VLESS + REALITY + TCP (Vision);
- «свои» (валидный Reality-клиент) уходят в туннель, «чужие» (браузер, сканер, провайдер) видят сайт-заглушку;
- опционально: выход в интернет через Cloudflare WARP, включается при установке;
- без панели, без графики, идемпотентно, с удалением и проверкой.

## 2. Что в исходной формулировке не сходится с реальностью

### 2.1. nginx не может определить VLESS

VLESS едет внутри TLS-сессии Reality. Для nginx это обычный зашифрованный TLS-поток: ключей Reality у него нет, расшифровать и «увидеть протокол» он не может. На L4 nginx видит только SNI/ALPN, а у Reality SNI — это домен маскировки, неотличимый от обычного браузера, зашедшего на тот же сайт. Эвристики по длине/содержимому ClientHello не работают и сами становятся отпечатком.

### 2.2. Reality нельзя терминировать TLS в nginx

Если nginx завершает TLS и проксирует содержимое в Xray, Reality ломается: клиент ждёт рукопожатие с целевым сайтом и проверку ключом Reality. Обратный прокси на L7 здесь невозможен в принципе.

### 2.3. `fallbacks` в Xray не работают с Reality

`fallbacks` — механизм для TCP+TLS: он срабатывает после расшифровки TLS. У Reality другой механизм: весь трафик, не прошедший проверку ключом, Xray сам проксирует на `target` (раньше `dest`). Это и есть встроенная «заглушка».

### 2.4. Cloudflare CDN не пропустит Reality

Оранжевое облако терминирует TLS на своей стороне, Reality через него не проходит. Для IPv4-доступа через Cloudflare нужен Spectrum (платно) или отдельный релей, а не CDN-прокси.

**Вывод:** роль «входных ворот» на 443 выполняет Xray, а не nginx. nginx остаётся на 80 и обслуживает заглушку на локальном порту. Поведение, которое нужно, сохраняется полностью: свой → туннель, чужой → сайт. Меняется только то, кто именно принимает решение.

## 3. Целевая архитектура (self-steal)

```
                 ┌────────────────────────── VPS ──────────────────────────┐
 клиент :443 ───▶│ Xray REALITY (VLESS / TCP / Vision)                     │
                 │   ├─ ключ верный  ──▶ outbound: direct │ WARP (WireGuard)│
                 │   └─ ключ неверный ─▶ 127.0.0.1:8443 (nginx, LE-сертификат)
                 │                              └─▶ сайт-заглушка          │
 клиент :80  ───▶│ nginx ──▶ ACME-челлендж + 301 на https://домен          │
                 └─────────────────────────────────────────────────────────┘
```

Почему так, а не «маскировка под microsoft.com»:

- с 2026 года Xray сам предупреждает при выборе apple.com / icloud.com / microsoft.com, а с июля 2026 — и доменов в зонах .ru / .ir / .cn;
- чужая крупная площадка на IP мелкого хостера выглядит неестественно и массово детектируется (волны блокировок Reality/TCP в ноябре 2025, феврале 2026, августе–сентябре 2026);
- «self-steal» (свой домен + свой сертификат + nginx на 127.0.0.1:8443) даёт совпадение домена, сертификата и IP. Для сканера и провайдера это обычный сайт.

Параметры Reality в этом режиме:

- `target` = `127.0.0.1:8443`, `xver` = `0` (иначе nginx получит лишний PROXY-заголовок и сайт не откроется);
- `serverNames` = ваш домен, он же в сертификате;
- отпечаток клиента — `firefox` (в 2026 рекомендуют именно его);
- домен нейтральный: блог, портфолио, визитка; без слов vpn/proxy/xray/node; не в зоне .ru.

Подключение идёт на IPv6-литерал, а SNI — домен: Reality сверяет SNI со списком `serverNames`, адрес клиента ему безразличен. Поэтому VPN работает сразу, ещё до того, как AAAA-запись разойдётся по резолверам.

## 4. Альтернативы и почему они не по умолчанию

| Вариант | Суть | Оценка |
|---|---|---|
| A. Self-steal (рекомендуемый) | 443 у Xray, заглушка в nginx на 127.0.0.1:8443 | Лучшая маскировка в 2026, минимум сущностей |
| B. Xray + чужой сайт | `target` = microsoft.com и т.п., nginx только на 80 | Проще, но в 2026 рискованно и Xray ругается |
| C. nginx первым на 443 (stream + ssl_preread) | nginx маршрутизирует по SNI: ваш домен → Xray, остальное → заглушка | Даёт логи/rate-limit на L4, но VLESS всё равно не видит, теряется реальный IP клиента, лишний хоп |
| D. nginx терминирует TLS | — | Невозможно с Reality |

Вариант C имеет смысл только как отдельная опция «хочу видеть SNI и резать мусор до Xray». В v1 не делаем.

## 5. Порты

| Порт | Кто слушает | Назначение |
|---|---|---|
| 443/tcp | Xray | Reality, единственный «настоящий» вход |
| 80/tcp | nginx | ACME, редирект, заглушка по HTTP |
| 127.0.0.1:8443 | nginx | HTTPS-заглушка для невалидных клиентов |
| 2408/udp (исходящий) | Xray | Endpoint Cloudflare WARP, только при `--warp` |

443/udp не используется: транспорт TCP.

## 6. Cloudflare WARP на выходе

### 6.1. Рекомендуемый способ — WireGuard-outbound внутри Xray

1. `wgcf register --accept-tos` → `wgcf generate` (или готовый профиль WARP).
2. Из профиля берём `PrivateKey`, `Address` (IPv4 + IPv6), `PublicKey`, `Endpoint`, `reserved` (3 байта из client_id).
3. В Xray добавляем outbound `wireguard` и делаем его выходом по умолчанию для всего трафика. `observatory` + balancer с `fallbackTag: direct` переключают на direct, если WARP перестал отвечать.

Плюсы: нет kernel-туннеля, нет policy routing, работает UDP (DNS, QUIC), обратный трафик приходит в тот же сокет Xray. Минусы: WARP периодически недоступен (в РФ блокируется), скорость и гео — на усмотрение Cloudflare.

### 6.2. Альтернативы

- `warp-cli mode proxy` → SOCKS5 `127.0.0.1:40000`, Xray-outbound `socks`. Просто, но нет UDP и лишний демон.
- `wg-quick` полный туннель. Требует `Table = off` + `ip rule`/fwmark, иначе можно потерять SSH. Для этой задачи избыточно.

### 6.3. Про «обратный трафик учитывать в nginx»

Не нужно. Ответ WARP приходит в UDP-сокет Xray, Xray отдаёт его в TCP-сессию клиента. nginx в этом пути не участвует вообще: он не проксирует туннель, а только отдаёт заглушку. Маршруты ядра и NAT не трогаем — именно поэтому WireGuard-outbound лучше `wg-quick`.

### 6.4. Ограничения WARP

- в РФ WARP блокируется, и если VPS/аплинк в РФ — туннель может не подняться;
- free-тариф не даёт проброса портов, режет SMTP, гео = ближайший PoP Cloudflare;
- WARP не «прячет» вас от Cloudflare и не заменяет нормальный exit-нод.

### 6.5. Блокировка RU-направлений (опция `--block-ru`, по умолчанию включена)

Правила ставятся до общего правила WARP:

```json
[
  {"type": "field", "domain": ["regexp:^.*\\.ru$", "regexp:^.*\\.xn--p1ai$", "regexp:^.*\\.su$"], "outboundTag": "block"},
  {"type": "field", "ip": ["geoip:ru"], "outboundTag": "block"}
]
```

Нужен `sniffing` с `routeOnly: true`, иначе домен не виден. Блокировка только исходящая: входящие с российских IP не режем, иначе вы потеряете доступ. Если в geosite вашей сборки есть `geolocation-ru`, его можно добавить в `domain` вместо TLD-регэкспов.

## 7. IPv4 / IPv6

### 7.1. Модель работы

Семья адресов клиента и выход Xray не связаны. Клиент открывает TCP-сессию к VPS по IPv6, Xray принимает VLESS, сам открывает исходящие соединения (IPv4 или IPv6, напрямую или через WARP) и возвращает ответы в ту же TCP-сессию. Трансляции между семьями адресов не требуется: это делают сокеты Xray, а не ядро.

```
клиент (IPv6) ⇄ TCP :443 ⇄ Xray ⇄ freedom (IPv4/IPv6) | wireguard → WARP
```

### 7.2. Чем клиент подключается

Принято: клиент ходит на IPv6-литерал `[2a01:...]:443`, а SNI — ваш домен. Это работает сразу, не дожидаясь, пока AAAA-запись разойдётся по резолверам: Reality сверяет SNI со `serverNames`, а адрес подключения ему безразличен.

```text
vless://UUID@[2a01:...]:443?encryption=none&flow=xtls-rprx-vision&security=reality&sni=DOMAIN&fp=firefox&pbk=PUBKEY&sid=SHORTID&type=tcp#NAME
```

Когда AAAA разойдётся, `--links` дополнительно напечатает вариант с доменом вместо литерала. На сертификат это не влияет: он всё равно выпускается на домен, без него self-steal не работает.

Почему не имя в ссылке сразу: если у имени есть A и AAAA, клиент может сначала пойти по IPv4, попасть в блокировку и провисеть до таймаута. Литерал исключает эту развилку.

### 7.3. Сертификат и DNS

- домен в режиме DNS only (серая туча), иначе AAAA указывает на Cloudflare и Reality не работает;
- LE HTTP-01 для AAAA-only имени выпускается по IPv6, при проблемах — DNS-01 через API регистратора;
- сертификат — ровно на имя из `serverNames` и SNI.

### 7.4. Настройки на сервере

- Xray: `"listen": "::"` (Go открывает dual-stack; при необходимости `net.ipv6.bindv6only=0`);
- проверка: `ss -lntp | grep 443` показывает `[::]:443`; `curl -4` и `curl -6` до 443 оба отвечают;
- firewall: ufw с `IPV6=yes` или nftables `family inet`; 80/443 открыты для обеих семей;
- исходящий IPv6 для direct-выхода проверить: `curl -6 -sS https://ifconfig.co`.

### 7.5. Если у клиента нет IPv6

Нужен IPv4-вход: A-запись на то же имя (клиент пойдёт по IPv4, если провайдер не блокирует) либо релей с IPv4. Для вашего сценария не требуется.

## 8. Скрипт

### 8.1. Артефакты

```
install.sh              # один файл, bash 5+, set -Eeuo pipefail
templates/              # конфиги и заглушка (или heredoc внутри install.sh)
README.md
PLAN.md
```

Распространение: `bash install.sh` или `curl -fsSL .../install.sh | bash -s -- --warp all`.

### 8.2. Этапы

0. Preflight: root, Debian 12 / Ubuntu 22.04–24.04, systemd, arch, свободные 80/443, DNS A/AAAA, наличие IPv6.
1. Пакеты: nginx, certbot, curl, jq, openssl, qrencode (опц.), ufw или nftables.
2. sysctl: BBR + fq, `tcp_fastopen=3`, `somaxconn`, `net.ipv6.bindv6only=0`.
3. Firewall: 80/443/tcp, SSH-порт; IPv6 в ufw включён.
4. Заглушка: `/var/www/<domain>`, vhost :80 (ACME + redirect), vhost `127.0.0.1:8443` (TLS 1.2/1.3, h2).
5. Сертификат: certbot HTTP-01 + deploy-hook на reload nginx; таймер продления.
6. Xray: установка закреплённой версии, генерация UUID / x25519 / shortId, конфиг, `xray run -test`, enable.
7. WARP (если включён): регистрация, outbound `wireguard`, routing, healthcheck через observatory с откатом на direct.
8. Проверка (см. §9), генерация ссылок и QR, отчёт в `/root/<host>-vpn.txt`.

### 8.3. Параметры

```
--mode selfsteal|foreign     # по умолчанию selfsteal
--domain example.com         # SNI, serverNames, сертификат
--endpoint-host [IPv6]       # адрес в ссылке; по умолчанию IPv6-литерал
--email admin@example.com
--cert-method http|dns|none  # none — использовать готовый сертификат
--cf-token TOKEN             # DNS-01 через Cloudflare
--warp off|all|smart         # по умолчанию all
--block-ru / --no-block-ru   # по умолчанию включено
--ssh-port 22
--users 1
--uuid <uuid>
--decoy-dir /var/www/site
--non-interactive
--uninstall | --status | --links | --add-user [name]
```

### 8.4. Идемпотентность и откат

- состояние в `/etc/xray-installer/state.json` (режим, домен, дата, версия);
- повторный запуск обновляет конфиг, сохраняя ключи, UUID и сертификат;
- `--regen-keys` / `--factory-reset` — только явно;
- перед изменениями бэкап в `/var/backups/xray-installer/<ts>/`;
- `trap ERR` → восстановление бэкапа и остановка юнитов;
- `--uninstall` удаляет только свои юниты, конфиги и vhost, чужие сайты nginx не трогает.

### 8.5. Безопасность и эксплуатация

- `chmod 600` на конфиг Xray (там приватный ключ), каталог 700;
- routing: `geoip:private` → block, bittorrent → block, чтобы VPS не стал открытым прокси;
- `sniffing` с `routeOnly`, чтобы не ломать адресацию;
- логи: journald + ограничение размера, access-log Xray выключен;
- обновление Xray и certbot по расписанию, `--status` показывает состояние;
- юнит Xray с `NoNewPrivileges`, `ProtectSystem=strict`, `CAP_NET_BIND_SERVICE`.

## 9. Проверка после установки

1. `xray run -test -c /usr/local/etc/xray/config.json`, `nginx -t`.
2. `ss -lntp` — 443 (xray), 80 и 127.0.0.1:8443 (nginx).
3. `curl -I http://<domain>` → 301; `curl -I https://<domain>` → 200 и заглушка.
4. `openssl s_client -connect <ip>:443 -servername <domain> -alpn h2` → сертификат домена, TLS 1.3.
5. Подключение реальным клиентом (v2rayN / Hiddify / sing-box) по ссылке.
6. `curl https://www.cloudflare.com/cdn-cgi/trace` через туннель → `warp=on` (если WARP включён).
7. С клиента: `curl -6 https://vpn.example.com` отдаёт заглушку; VLESS-подключение по IPv6, `curl ifconfig.me` показывает выходной IP (WARP или VPS).
8. Внешний чекер: 443/tcp и 80/tcp открыты по IPv4 и IPv6.

Ссылка клиента:

```text
vless://UUID@[IPv6]:443?encryption=none&flow=xtls-rprx-vision&security=reality&sni=DOMAIN&fp=firefox&pbk=PUBLIC_KEY&sid=SHORT_ID&type=tcp#NAME
```

`--links` печатает её же с доменом вместо литерала, когда AAAA уже резолвится. `--add-user` дописывает нового клиента в конфиг, перезапускает Xray и печатает ссылку для него.

## 10. Риски 2026

- Reality/TCP периодически блокируется на уровне ТСПУ; self-steal снижает риск, но не устраняет. Запасной канал (VLESS + XHTTP/TLS на 443 или CDN-транспорт) стоит заложить в roadmap, но не в v1.
- WARP в РФ может быть недоступен.
- Домен и сертификат обязательны для self-steal; без домена остаётся режим B с чужим сайтом и его рисками.

## 11. Открытые вопросы

1. Домен для SNI/сертификата и способ выпуска: HTTP-01 (порт 80) или DNS-01 (токен Cloudflare). Если AAAA ещё не виден снаружи, HTTP-01 может не пройти — тогда нужен DNS-01.
2. Где стоит VPS: вне РФ — WARP заработает; в РФ — WARP, скорее всего, не поднимется, и скрипт уйдёт в direct с предупреждением.

## 12. Порядок реализации

1. `install.sh`: preflight, пакеты, sysctl, firewall, nginx-заглушка, сертификат, Xray, WARP, проверки, ссылки.
2. Подкоманды `--status`, `--links`, `--add-user`, `--uninstall`.
3. `README.md`: быстрый старт, флаги, как добавить пользователя, как перевыпустить сертификат, диагностика.
4. Прогон на чистой Ubuntu 22.04 (IPv6-only вход + dual-stack выход), проверка по §9.
